## 1. 项目概述

Firefly Studio 是一款基于 **Electron** 的 3D 数字人桌面应用，集成了语音识别、语音合成、大语言模型对话、音乐播放等功能。项目采用 **C++ 原生模块** 处理音频相关的高性能计算任务，并支持在 VSCode 中直接打断点调试 C++ 代码。

### 1.1 核心目标

- **本地优先**：所有语音识别、语音合成、音频处理均在本地完成，保护用户隐私
- **高性能**：使用 C++ 原生模块处理音频能量计算、VAD 检测、麦克风采集等任务
- **可调试**：支持在 VSCode 中同时调试 JavaScript（主进程/渲染进程）和 C++（原生模块）
- **可扩展**：模块化设计，支持接入不同的 LLM 后端、TTS 引擎、ASR 模型

### 1.2 应用场景

- 个人 AI 助手（语音交互）
- 数字人直播/录播
- 语音对话机器人
- 本地离线 AI 助手

## 2. 整体架构

### 2.1 架构分层

Firefly Studio 采用典型的 Electron 三层架构，并在此基础上扩展了 C++ 原生层和后端服务层：

```
┌─────────────────────────────────────────────────────────────────┐
│                        渲染进程 (Renderer)                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐ │
│  │  React UI   │  │  3D 数字人  │  │     音乐播放器           │ │
│  │  (App.jsx)  │  │  (three.js) │  │   (MusicPlayer.jsx)     │ │
│  └──────┬──────┘  └──────┬──────┘  └────────────┬────────────┘ │
│         │                │                          │              │
│  ┌──────┴────────────────┴──────────────────────────┴────────────┐ │
│  │              Hooks 层 (useResolveChat, useMic, ...)           │ │
│  └──────────────────────────────┬────────────────────────────────┘ │
└─────────────────────────────────┼─────────────────────────────────┘
                                  │ IPC (contextBridge)
┌─────────────────────────────────┼─────────────────────────────────┐
│                        主进程 (Main)                              │
│  ┌──────────────────────────────┴────────────────────────────────┐ │
│  │                    Electron 主进程入口                          │ │
│  │              (窗口管理 / 生命周期 / IPC 路由)                  │ │
│  └──────┬───────────────────┬───────────────────┬───────────────┘ │
│         │                   │                   │                 │
│  ┌──────┴──────┐    ┌──────┴──────┐    ┌──────┴──────┐        │
│  │   ASR 服务   │    │   TTS 服务   │    │  音频播放    │        │
│  │  (asr.js)   │    │  (tts.js)   │    │ (CoreAudio)  │        │
│  └──────┬──────┘    └──────┬──────┘    └──────┬──────┘        │
└─────────┼───────────────────┼───────────────────┼─────────────────┘
          │ N-API             │ N-API             │ N-API
┌─────────┼───────────────────┼───────────────────┼─────────────────┐
│                   C++ 原生模块 (Native Module)                    │
│  ┌───────────────────────────────────────────────────────────────┐ │
│  │                    N-API 入口 (addon.cc)                      │ │
│  │              (句柄表 / JS 绑定 / 生命周期管理)                 │ │
│  └──────┬───────────────┬───────────────┬───────────────────────┘ │
│         │               │               │                         │
│  ┌──────┴──────┐ ┌──────┴──────┐ ┌──────┴──────┐               │
│  │ 音频引擎     │ │ 麦克风采集   │ │ ASR 封装     │               │
│  │(audio_engine)│ │(mic_capture)│ │(asr_whisper) │               │
│  │  RMS/VAD     │ │ CoreAudio    │ │ Whisper.cpp  │               │
│  └─────────────┘ └─────────────┘ └─────────────┘               │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐ │
│  │                   第三方 C++ 库                                │ │
│  │  Whisper.cpp (ASR)  │  RNNoise (降噪)  │  Piper (TTS)       │ │
│  └───────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
                                  │ HTTP (SSE)
┌─────────────────────────────────┼─────────────────────────────────┐
│                      后端服务 (Backend)                            │
│  ┌──────────────────────────────┴────────────────────────────────┐ │
│  │                    LLM 对话服务                                │ │
│  │         (resolve-studio / 内置 standalone.js)                 │ │
│  └──────────────────────────────┬────────────────────────────────┘ │
│                                 │ HTTP                              │
│  ┌──────────────────────────────┴────────────────────────────────┐ │
│  │                    大语言模型 (LLM)                             │ │
│  │         (OpenAI / DeepSeek / 本地 Ollama / 其他)              │ │
│  └───────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 进程间通信

| 通信方式 | 方向 | 用途 |
|---------|------|------|
| **IPC (contextBridge)** | 渲染进程 ↔ 主进程 | 安全的 API 调用（麦克风控制、TTS 合成、文件操作等） |
| **N-API** | 主进程 ↔ C++ 原生模块 | 高性能音频处理（RMS 计算、VAD 检测、麦克风采集、ASR 推理） |
| **HTTP/SSE** | 渲染进程 ↔ 后端服务 | LLM 对话（流式输出）、工具调用 |
| **HTTP** | 后端服务 ↔ LLM 提供商 | 大语言模型 API 调用 |

## 4. 核心模块

### 4.1 渲染进程模块

#### 4.1.1 App.jsx（主应用组件）

**职责**：
- 管理全局状态（聊天消息、数字人状态、音乐播放状态、面板布局）
- 协调各个子组件（Stage、MusicPlayer、ChatPanel、Settings）
- 处理音乐闪避逻辑（数字人说话时降低音乐音量）
- 管理主题切换、面板布局持久化

**关键状态**：
- `messages`：聊天消息列表
- `isSpeaking`：数字人是否正在说话
- `isSinging`：是否正在播放音乐
- `currentCharacter`：当前数字人角色
- `panelOpen` / `leftPanelWidth` / `rightPanelWidth`：面板布局状态

#### 4.1.2 Stage.jsx（3D 数字人舞台）

**职责**：
- 管理 3D 场景（相机、灯光、地面、背景）
- 加载和切换数字人模型（VRM/GLB）
- 处理数字人动画（眨眼、口型同步、表情、手势）
- 响应音频能量，驱动口型同步

**支持的模型格式**：
- **VRM**：VRoid 二次元风格，自带面部 blendshape（眨眼+口型）
- **GLB**：Ready Player Me / Avaturn 写实风格

**关键技术**：
- `@react-three/fiber`：React 声明式 3D 渲染
- `@pixiv/three-vrm`：VRM 模型加载和动画
- `audioEnergy`：实时音频能量（0~1），用于口型同步

#### 4.1.3 MusicPlayer.jsx（音乐播放器）

**职责**：
- 管理播放列表（添加/删除/切换歌曲）
- 音频播放控制（播放/暂停/上一首/下一首）
- 音效处理（均衡器 EQ、混响、音量归一化）
- 播放模式（顺序/随机/循环/单曲）
- 播放列表持久化（localStorage）

**音效处理链**：
```
音频源 → 音量归一化 → 均衡器(EQ) → 混响(Reverb) → 主音量 → 输出
```

**关键技术**：
- Web Audio API：浏览器音频处理
- `createAudioEffectsChain`：自定义音效处理链
- `localStorage`：播放列表持久化

#### 4.1.4 useResolveChat.ts（LLM 聊天 Hook）

**职责**：
- 管理 LLM 对话状态（发送/接收/错误）
- 处理 SSE 流式输出
- 累积流式响应，更新消息列表
- 处理对话错误和重试

**关键功能**：
- `send(message)`：发送消息到 LLM 后端
- `abort()`：中止当前对话
- `accumulated`：累积的流式响应文本
- SSE 事件解析（message / delta / done / error）

#### 4.1.5 useMic.js（麦克风采集 Hook）

**职责**：
- 管理麦克风采集状态（启动/停止）
- 处理音频帧回调（RMS 能量、VAD 检测）
- 自适应阈值调整
- 语音段检测和拼接

**关键功能**：
- `startMic()`：启动麦克风采集
- `stopMic()`：停止麦克风采集
- `onFrame`：音频帧回调（包含 RMS 能量和 VAD 结果）
- `onSpeechSegment`：语音段回调（完整的语音段 PCM 数据）

### 4.2 主进程模块

#### 4.2.1 index.js（主进程入口）

**职责**：
- 创建和管理 BrowserWindow
- 注册 IPC 处理器（contextBridge 暴露的 API）
- 加载 C++ 原生模块（firefly_native.node）
- 管理应用生命周期（启动/退出/异常处理）
- 启动内置后端服务（如果配置）

**关键功能**：
- `loadNativeModule()`：加载 C++ 原生模块，处理加载失败
- `registerIPCHandlers()`：注册所有 IPC 处理器
- `createMainWindow()`：创建主窗口，配置 webPreferences
- 守护进程管理（ASR/TTS 服务的异常重启）

#### 4.2.2 asr.js（ASR 语音识别服务）

**职责**：
- 管理 Whisper.cpp 模型加载和推理
- 处理语音段的语音识别
- 流式识别支持（边说边识别）
- 识别结果后处理（标点、大小写、分段）

**关键功能**：
- `loadModel(modelPath)`：加载 Whisper 模型
- `transcribe(audioBuffer)`：对音频段进行语音识别
- `transcribeStream(audioStream)`：流式语音识别
- `postProcess(text)`：识别结果后处理

#### 4.2.3 tts.js（TTS 语音合成服务）

**职责**：
- 管理 TTS 引擎（Piper）
- 文本预处理（分段、数字归一化、表情符号过滤）
- 语音合成和音频播放
- 中英文自动切换

**关键功能**：
- `synthesize(text, options)`：文本转语音
- `playAudio(audioBuffer)`：播放合成的音频
- `stopAudio()`：停止音频播放
- `preprocessText(text)`：文本预处理（分段、归一化）

**TTS 引擎**：
- **Piper**（默认）：本地离线，MIT 许可证，无需联网，支持中英文自动切换

### 4.3 C++ 原生模块

#### 4.3.1 addon.cc（N-API 入口）

**职责**：
- N-API 模块初始化
- JS 函数绑定（导出给 JavaScript 的 API）
- 句柄表管理（管理 C++ 对象的生命周期）
- 异步任务处理（避免阻塞 JS 事件循环）

**导出的 API**：
- `audioEnergy.create()`：创建音频引擎实例
- `audioEngine.calculateRMS(buffer)`：计算 RMS 能量
- `audioEngine.detectVAD(buffer)`：VAD 语音活动检测
- `micCapture.start(options)`：启动麦克风采集
- `micCapture.stop()`：停止麦克风采集
- `asr.loadModel(path)`：加载 Whisper 模型
- `asr.transcribe(buffer)`：语音识别

#### 4.3.2 audio_engine（音频引擎）

**职责**：
- 音频帧的 RMS（均方根）能量计算
- VAD（语音活动检测）
- 自适应阈值调整
- 音频帧缓冲和拼接

**关键算法**：
- **RMS 计算**：`sqrt(sum(x^2) / n)`，衡量音频信号的能量
- **VAD 检测**：基于能量阈值和持续时间的语音活动判断
- **自适应阈值**：根据背景噪声动态调整检测阈值

#### 4.3.3 mic_capture（麦克风采集）

**职责**：
- 使用 CoreAudio 采集麦克风音频
- 音频格式转换（采样率、位深、声道）
- 音频帧回调（按固定帧大小回调给 JS）
- 采集设备管理（枚举/选择/默认设备）

**关键技术**：
- **CoreAudio**：macOS 原生音频框架，低延迟
- **Audio Queue Services**：音频队列服务，用于音频采集
- **环形缓冲区**：减少内存分配，提高性能

#### 4.3.4 asr_whisper（Whisper ASR 封装）

**职责**：
- 封装 Whisper.cpp 的 C API
- 模型加载和管理
- 音频预处理（重采样、归一化）
- 推理结果解析（文本、时间戳、置信度）

**关键技术**：
- **Whisper.cpp**：OpenAI Whisper 的 C++ 实现，支持本地离线推理
- **GGML**：Whisper.cpp 使用的张量计算库，支持 CPU/GPU 加速
- **量化模型**：支持 int8/q5_0/q8_0 等量化格式，减少内存占用

         ▼

### 5.2 文字聊天流程

```
用户输入文字 → 发送消息
        │
        ▼
渲染进程 useResolveChat.send()
        │
        ▼
HTTP POST → 后端服务 (resolve-studio)
        │
        ▼
后端服务 → LLM API (OpenAI/DeepSeek)
        │
        ▼
LLM 流式响应 (SSE)
        │
        ▼
渲染进程解析 SSE 事件
        │
        ├─ message 事件 → 创建消息
        ├─ delta 事件 → 追加文本（打字机效果）
        ├─ done 事件 → 消息完成，触发 TTS
        └─ error 事件 → 显示错误
```

### 5.3 音乐播放与闪避流程

```
用户添加歌曲 → 播放列表 (localStorage)
        │
        ▼
用户点击播放 → MusicPlayer.play()
        │
        ▼
Web Audio API 创建音频源
        │
        ▼
音效处理链：音量归一化 → EQ → 混响 → 主音量
        │
        ▼
音频输出 → 扬声器
        │
        ├─ 实时能量分析 → 数字人动作（可选）
        │
        ▼
数字人开始说话 (TTS)
        │
        ▼
音乐闪避：主音量降低 (ducking)
        │
        ▼
数字人说话结束
        │
        ▼
音乐恢复：主音量恢复正常
```

## 7. 设计决策与权衡

### 7.1 为什么使用 C++ 原生模块？

**决策**：音频能量计算、VAD 检测、麦克风采集等高性能任务使用 C++ 原生模块实现。

**原因**：
- **性能**：C++ 比 JavaScript 快 10-100 倍，适合实时音频处理
- **低延迟**：麦克风采集和音频处理需要低延迟，C++ 可以更好地控制时序
- **平台集成**：CoreAudio 等原生音频框架在 C/C++ 中更易用
- **可调试**：支持在 VSCode 中打断点调试 C++ 代码

**权衡**：
- 开发复杂度增加（需要同时维护 JS 和 C++ 代码）
- 构建流程复杂（需要 node-gyp 和 electron-rebuild）
- 跨平台需要分别实现（目前仅支持 macOS）

### 7.2 为什么选择 Whisper.cpp 而不是云端 ASR？

**决策**：使用 Whisper.cpp 本地离线语音识别，而不是云端 ASR 服务。

**原因**：
- **隐私保护**：语音数据不上传，完全在本地处理
- **无需联网**：离线可用，不依赖网络连接
- **成本**：免费开源，无 API 调用费用
- **延迟可控**：本地推理，延迟可预测

**权衡**：
- 准确率略低于云端服务（尤其是在嘈杂环境下）
- 需要下载模型文件（base 模型约 140MB）
- 占用本地计算资源（CPU/内存）

### 7.3 为什么选择 Piper 作为 TTS 引擎？

**决策**：使用 Piper 本地离线 TTS 作为唯一的 TTS 引擎。

**原因**：
- **隐私保护**：文本数据不上传，完全在本地处理
- **许可证友好**：MIT 许可证，无传染性，可用于商业项目
- **速度快**：基于 ONNX runtime，推理速度快，延迟低
- **无需联网**：离线可用

**权衡**：
- 音质不如某些在线 TTS 服务
- 语音种类较少（目前主要支持中文小雅和英文 Amy）
- 需要下载模型文件（每个约 60MB）

### 7.4 为什么推荐 resolve-studio 作为后端？

**决策**：推荐使用 resolve-studio 作为 LLM 后端，而不是仅使用内置 standalone.js。

**原因**：
- **完整能力**：resolve-studio 提供完整的 agent loop、工具调用、PSE 三角色
- **工具生态**：丰富的预定义工具（文章写作、投资分析、简历优化、面试题生成等）
- **会话管理**：完整的会话历史管理和持久化
- **可扩展性**：支持自定义工具和插件

**权衡**：
- 需要额外启动 resolve-studio 服务
- 配置相对复杂（需要配置 LLM API key 等）
- 资源占用更高（两个服务同时运行）

### 7.5 为什么使用 SSE 而不是 WebSocket？

**决策**：使用 SSE（Server-Sent Events）进行 LLM 流式输出，而不是 WebSocket。

**原因**：
- **简单**：SSE 基于 HTTP，实现简单，无需复杂的握手和协议
- **兼容性好**：所有现代浏览器都支持 SSE
- **自动重连**：SSE 内置自动重连机制
- **单向通信足够**：LLM 流式输出只需要服务器向客户端推送，不需要双向通信

**权衡**：
- 仅支持服务器到客户端的单向通信（无法通过同一连接发送消息）
- 不支持二进制数据（仅支持文本）
- 某些代理/防火墙可能会缓冲 SSE 响应
